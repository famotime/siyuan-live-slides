# ADR-0001：功能开关采用构建期常量而非运行时设置

- 状态：已接受（Accepted）
- 日期：2026-11-06
- 关联：`src/feature-flags/feature-flags.ts`、GLOSSARY「功能开关」

## 背景

需要为部分功能（Pro 模式、演讲者视图、导出 HTML、导出 PDF、导出图片、导入、AI 讲稿——演讲者视图为后续迭代按同一机制追加）提供独立启停能力，用于在发布不同形态的构建产物时裁剪功能入口（例如面向特定分发渠道的精简版）。插件当前没有任何 feature-flag 机制，所有 Tab、按钮、命令在 onload 时无条件注册。

有两种可选形态：

1. **构建期常量**：入库的配置模块，编辑后重新构建生效；代码始终打包，仅裁剪入口（参考 siyuan-sketch-note 的 `alpha-feature-config.ts` 模式）。
2. **运行时设置**：插件设置面板或 storage 中的开关，用户可在运行时切换。

## 决策

采用**构建期常量**方案：

- `src/feature-flags/feature-flags.ts` 导出 `FeatureKey` 类型与 `FEATURE_FLAGS` 布尔表（默认全 `true`），以及 `isFeatureDisabled(key)` / `isFeatureEnabled(key)` 判断函数。
- 各 UI 组件以 `v-if="isFeatureEnabled(...)"` 裁剪按钮/图标/菜单；`registerPluginCommands` 以条件语句跳过被关闭功能的命令注册。
- 不使用 Vite `define` 做死代码消除：收益仅为包体减小，但要求每个消费点内联常量表达式才能被摇树，复杂度与测试成本明显上升，与「取消入口」的需求不匹配。

同时记录两个本轮敲定的语义边界（未来读者最容易困惑之处）：

1. **没有名为「沙箱」的开关**。最初候选的「沙箱」开关经讨论重定义为 `proMode`：沙箱预览是插件的核心价值，永远保留；可裁剪的是 Pro 模式（本地 Slidev CLI DevServer）相关入口。若存在「关闭沙箱但保留 Pro 模式」的中间态，会出现普通用户环境「有开关无预览」的空窗，故不设此开关。
2. **`aiScript` 只裁剪 AI 生成类入口**。手动讲稿体系（讲稿块定位/追加/批量管理、「设为讲稿备注」开关）是独立价值，保留不动；讲稿块仍是演讲者视图的数据载体。

## 后果

- 正面：零构建链路改动；`npm test` 可直接覆盖门控逻辑（mock 开关模块验证命令条件注册）；配置入库可审查、可追溯每次发布形态的差异。
- 正面：被关闭功能的代码仍留在 bundle 中，未来若改为运行时设置，无需找回被裁剪的实现。
- 负面：包体不会因关闭功能而减小；被关闭功能的代码仍随 bundle 分发（当前可接受）。
- 负面：修改开关必须重新构建并重新分发插件，不能热切换。若未来出现「用户自行启停功能」的真实需求，应另立 ADR 评估迁移到运行时设置（可复用同一批 FeatureKey 语义）。
- 维护约束：新增可裁剪功能时，必须同时扩展 `FeatureKey`、布尔表、本 ADR 的开关清单，并在测试中补充对应门控用例，保证「入口全裁剪」的承诺不破。
