> 适用版本：`siyuan-slidev` v0.9.0+
> 状态：P0/P1 优化已实施，本文含修复复盘、内核契约速查与后续演进建议
> 最后更新：2026-10-08
> 关联提交：`22af20f`（P0 编译放大治理）、`def2d76`（P1 内核往返收敛）、`eef716b`（索引语义与排序键修复）

## 一、问题现象与实测定位

### 1.1 现象清单（均来自真实使用环境实测）

| # | 现象 | 实测数据 | 定位结论 |
|---|---|---|---|
| 1 | 切换到复杂大文档后内核进程 CPU 飙至 40%+，**关闭预览窗口也不降**，切到简单文档并等待后回落 | 编辑器持续操作时内核请求不断 | 编译由编辑器事务驱动且无消费者门闩，编译还会重叠积压 |
| 2 | 关闭/打开预览时同步表现异常；编辑后预览"**慢一步**"，下一次编辑才显示上一次的结果 | **删一次内容只出现 1 个 `getChildBlocks`**、无回退告警 | 内容取自异步落库的 SQL 索引，索引滞后于实时块树 |
| 3 | 超级块左中右分栏内容**错乱渲染**（左边的渲染到右边），编辑时**位置跳变** | 索引行序与文档顺序不一致 | `blocks.sort` 被误当作文档位置使用 |

### 1.2 关键教训：三个现象背后是三条独立的内核语义假设

这三个问题都不是"性能调优不够"，而是**对内核行为的假设错误**。它们的共同特征是：**在本机无法通过单元测试发现，只有真实内核语义 + 真实文档形态才会暴露**。因此本文第二节把相关内核契约列为速查表，后续任何触及编译链路的改动都应先比对这张表。

## 二、内核契约速查表（本次修复的核心产出）

> 引用位置均为 `siyuan-note` 内核源码。凡涉及块结构、索引、顺序的判断，**必须先在此表核对，不得凭直觉推断**。

| 契约点 | 结论 | 源码位置 |
|---|---|---|
| **SQL 索引是异步落库的** | `blocks` 表由索引队列批量写入，提交后经 `time.AfterFunc(50ms)` 触发，属**最终一致**，短暂滞后于实时块树 | `kernel/sql/queue.go:177`、`kernel/sql/index_queue.go` |
| **`blocks.sort` 不是文档位置** | 它是**块类型权重**：标题=5、段落/代码/表格=10、列表=20…… | `kernel/sql/database.go` 的 `nSort()` |
| **`created` 不可作位置** | 秒级时间戳，同秒创建的块顺序未定义 | `blocks` 表 schema |
| **文档顺序的权威来源** | `/api/block/getDocBlocksOrders`：对实时块树 `ast.Walk` 前序遍历，返回全文档块 id 的文档序 | `kernel/model/blockinfo.go` 的 `getDocBlocksOrdersInTree()` |
| **索引 `parent_id` 的特殊语义** | 处于标题块下方的块，`parent_id` 会被覆写为最近的标题祖先（`treenode.HeadingParent`） | `kernel/sql/database.go` 的 `buildBlockFromNode()` |
| **索引与实时 API 同源同函数** | `getChildBlocks` 的 Content/Markdown/Type/SubType 同样由 `sql.BuildBlockFromNode` 生成，故同一块的字段可直接字符串比对 | `kernel/model/block.go` 的 `childBlockFromNode()` |
| **容器块的 content/markdown 是子树序列化** | 容器块内容 = 整棵子树的导出结果，因此子树内任何改动都会体现在该容器上（也让"是否滞后"可以被父级观测） | `kernel/sql/database.go` 的 `ExportNodeStdMd` 调用 |
| **索引更新以树为单位（另有单节点例外）** | 队列操作携带 `indexTree` / `upsertTree` / `removeTreePath`，整树重写；另有 `index_node` 单节点操作。**注意：本插件的正确性不依赖索引更新的原子性**——只要"容器内容是其子树的序列化"成立，任何一处滞后都会体现为某个顶层容器的不一致，从而触发该子树重建 | `kernel/sql/queue.go` 的 `dbQueueOperation` |
| **`blocks` 表无 `sub_type` 列** | 列名为 **`subtype`**；写错列名的 SQL 会报错，若被 `.catch` 吞掉则会静默失效 | `kernel/sql/database.go` 建表语句 |
| **`idx_blocks_root_id` 存在** | 按 `root_id` 拉取整篇文档的索引行是走索引的，非全表扫描 | `kernel/sql/database.go` 建索引语句 |
| **面板元素的隐藏机制** | 后台页签 / 折叠面板由宿主在**面板元素自身**加 `.fn__none`（`display:none !important`）；插件 `addTab/addDock` 拿到的正是该面板元素 | `app/src/layout/Wnd.ts`（`panelElement.classList.add("fn__none")`）、`app/src/layout/dock/Custom.ts`（`this.element = options.tab.panelElement`） |
| **桌面端本地内核模式禁用系统代理探测** | 启动时追加 `--no-proxy-server`，随后**仅**对主窗体 Session 调用 `setProxy` 下发「设置 → 网络代理」 | `app/electron/main.js` |
| **代理配置按 Session 生效** | `session.setProxy()` 只作用于该 Session；`<webview partition="...">` 会落到另一个从未配置代理的 Session | Electron 语义 + `app/electron/main.js` |
| **远程内核模式禁用 `<webview>`** | 主窗体 `webviewTag: false`，且注册 `will-attach-webview` 直接 `preventDefault()` | `app/electron/main.js` |
| **本地 HTML 资源需 `?iframe=true`** | 内核仅在请求带 `iframe=true` 时以 `text/html` + CSP 内联输出，否则 HTML 属未列入内联白名单的类型而**强制附件下载** | `kernel/server/serve.go` 的 `secureAssetContentHeaders()`、`kernel/model/assets.go` 的 `IsHTMLAssetIFrameSrc()` |

## 三、修复方案

### 3.1 数据源分工三原则（`src/compiler/document-compiler.ts`）

一次编译所需的全部信息，按**权威性**拆给三个来源，不再混用：

| 关注点 | 权威来源 | 理由 |
|---|---|---|
| **同层兄弟顺序** | `getDocBlocksOrders`（实时、`ast.Walk` 前序） | SQL 中不存在可代表位置且同步的列 |
| **父子结构（谁的子块）** | SQL 索引行的 `parent_id` | 结构关系可靠，且一次 SQL 即可全量取得 |
| **内容 / IAL** | 实时 `getChildBlocks`（顶层）+ 新鲜度校验后的索引行 | 内容必须实时；IAL 另有即时覆盖层兜底 |

一次编译的固定内核调用数为 **5**（`getBlockAttrs` + `getChildBlocks` + `getDocBlocksOrders` + 2 次 SQL），与文档容器数无关；旧实现为 O(容器数) 次串行 `getChildBlocks`，复杂文档下达数百次。

### 3.2 按子树精确重建（`analyzeIndexContent()` + `rebuildSubtreeLive()`）

索引滞后不整体判死，而是**只重建确实滞后的子树**：

| 情形 | 处置 | 额外内核调用 |
|---|---|---|
| 叶子顶层块内容滞后 | 用实时值就地修正（其下无子树，不影响其它索引行） | 0 |
| 容器顶层块内容滞后 | 只重建该子树（递归走实时 `getChildBlocks`） | 该子树内的容器数 |
| 索引缺失的实时顶层块（新增） | 按实时数据补齐 | 0（叶子）/ 该子树 |
| 索引残留行（已删除块） | 依实时文档序剔除（**文档序同时是成员权威**） | 0 |
| 缺少文档序或索引不可用 | 回退全量实时路径 | O(全文档容器数) |

### 3.3 消费者门闩三态（`src/sync/compile-consumer-gate.ts`）

自动编译仅在"有人看得到结果"时才值得做。可见性判定以**宿主自身的隐藏机制**为主信号：

| 状态 | 语义 | 编译策略 |
|---|---|---|
| `none` | 预览页签与 Dock 均未挂载 | **完全不编译**，只登记脏文档 |
| `hidden` | 已挂载但被宿主隐藏（后台页签 / 折叠面板 / 窗口最小化） | 有界低频（600ms） |
| `visible` | 至少一个消费者真实可见 | 编辑器静默 150ms 后编译 |

- 主信号：`element.closest('.fn__none')`（**零布局开销**，且与宿主的隐藏机制同源）
- 辅助信号：`IntersectionObserver`（异步缓存，用于覆盖非 `.fn__none` 方式隐藏的情形）
- 兜底：一次性 2s 低频校验 + 首层子元素检查，防止观察器误报导致预览**永久停更**
- 判定方向刻意**偏向"继续编译"**（`visible = 观察器报可见 ∪ 宿主未标记隐藏`），宁可多编译，不可停更

### 3.4 编译单飞与代际丢弃（`src/sync/compile-scheduler.ts`）

- 同一时刻只允许一次编译在执行，期间到达的请求合并为"最新文档胜出"的 pending
- 结果带代际号，过期或文档已切走则丢弃，避免旧结果覆盖新内容
- 补跑重新走脏标记与 150ms 防抖，保证"编辑器静默后才编译"

### 3.5 逐光标属性解析三层收敛（`src/sync/inspector-sync-cache.ts`）

`selectionchange` 在敲字时逐字符触发，此前每次最多 4 次 `getBlockAttrs` 内核往返。现按三级收敛：

1. **即时覆盖层**（属性变更经 ws 事务写入，优先级最高，内存命中）
2. **编译模型 IAL 索引**（内存命中）
3. **短 TTL 缓存**（400ms，合并重复查询）

另对同一块的光标联动加 150ms 节流（**跨块立即同步**，翻页链路不受影响）。

## 四、适用场景

### 4.1 收益明显的场景

| 场景 | 收益来源 |
|---|---|
| 长时间在**复杂大文档**（大量列表 / 超级块）中编辑 | N+1 消除：单次编译内核往返由 O(容器数) 降为常数级 |
| 预览页签切到后台、或只开 Dock 面板时继续编辑 | 门闩三态：由"持续全量编译"降为有界低频 |
| 关闭预览与 Dock 后编辑 | 门闩 `none`：内核请求**归零** |
| 频繁敲字 / 移动光标 | 属性解析三层收敛 + 同块节流：逐字符内核查询近乎归零 |
| 大文档频繁切换 | 单飞合并 + 代际丢弃：不再重叠积压，切走即降 |
| 桌面端连接**远程/容器内核** | 速览抽屉降级走 iframe（该模式宿主禁用 `<webview>`） |
| 公司内网代理环境 | 抽屉复用宿主默认 Session，继承「设置 → 网络代理」 |

### 4.2 收益有限或不适用

| 场景 | 说明 |
|---|---|
| 极小文档（几个块） | N+1 本来就只有几次调用，优化空间有限 |
| 单次查看、不编辑 | 无编辑事件 → 无编译触发 |
| 编辑**超大列表**（数十项起） | 见 §6 残余边界：容器内取实时内容需逐容器调用 |
| 需要承载 HTML 完整源能力 | 速览抽屉的 HTML 受内核 CSP 限制（`sandbox allow-scripts`：无 `localStorage`、`fetch` 受同源约束），此限制由内核施加，无法绕过 |

## 五、验证方法（可复现）

| 目标 | 步骤 | 预期 |
|---|---|---|
| 关闭消费者后内核请求归零 | 关闭预览与 Dock，在编辑器敲字，F12 → Network 过滤 `getChildBlocks` | **0 个请求** |
| 编辑叶子块走快速路径 | 打开预览，修改一个段落，观察 Network | **1 个** `getChildBlocks`（顶层那次），预览立即更新 |
| 编辑容器块只重建该子树 | 修改列表 / 超级块内部，观察 Network | 仅该子树的**几次**调用；**未变更**的其它子树不出现请求 |
| 分栏顺序正确 | 构造成"左中右"三栏超级块并在各栏编辑 | 顺序稳定为左→中→右，编辑时不跳变 |
| 慢路径诊断 | 若偶发变慢，F12 → Console | 打印 `索引结构不可用，回退逐容器查询… 原因=`，可直接定位 |
| 代理继承 | 内网环境点击外网链接 | 抽屉可直接打开（前提：思源「设置 → 网络代理」已配置） |

## 六、残余边界与已知限制

1. **编辑超大列表**：容器内取实时内容必须逐容器调用，故编辑一个数十项的列表仍会对该列表内部逐项调用（O(项数)）。这比"全文档遍历"好得多，但未彻底消除——彻底方案见 §7.1。
2. **门闩依赖宿主 DOM 约定**：可见性主信号依赖 `.fn__none` 这一宿主实现细节。已用"或"语义偏向继续编译，并加 2s 兜底校验，最坏情况为"多编译"而非"停更"。
3. **索引不可用时的降级**：老内核或受限环境缺少 `getDocBlocksOrders` 时回退全量实时路径（正确但慢），控制台有明确告警。
4. **无法端到端自动化**：本机无可用思源运行时，编译链路的验证依赖内核源码核对 + 单元测试 + 真机实测三方印证。**任何触及该链路的改动都应在真机上按 §5 过一遍。**

## 七、后续优化建议（按优先级）

### 7.1 P1：事务 op id 路径级重建（解决 §6.1）

当前"容器内容滞后"只能靠"容器内容与实时不一致"来发现，因而必须重建**整棵**滞后子树。若把 ws 事务的 `op.id`（被编辑块 id）接入编译器，即可：

- 只沿"被编辑块 → 其祖先"这条路径刷新，其它兄弟节点直接沿用索引行
- 编辑超大列表时，调用数从 O(项数) 降到 O(深度)

实现要点：`patchThematicBreakTransactions` 已能看到全部 `doOperations`，只需把近期 op id 集合（带短暂 TTL）传给 `DocumentCompilerService.compile()` 作为重建提示；需注意事务重放（undo/redo）与跨文档事务的过滤。

### 7.2 P1：大文档保护与用户可退路

`src/settings.ts` 目前仅有 3 个配置键，**用户没有关闭自动编译的开关**：

- 增加「自动编译」开关（关闭时仅响应显式编译：命令与刷新按钮）
- 增加块数阈值：超过阈值自动降级为"仅手动编译"，并在 Dock 顶部提示与提供一键编译

### 7.3 P2：降低单次编译的固有成本

- `purgeStaleDomSlidevAttrs` 目前每次编译全文档 DOM 巡检，可收敛为"仅巡检本次编译涉及的块集合"
- 编译耗时埋点常驻化：`console.debug` 输出编译耗时与路径（索引/子树重建/全量回退），便于长期观测与回归定位

### 7.4 P3：增量编译

以"页（divider 分隔的幻灯片）"为粒度做增量：仅重建内容发生变化的页，其余页复用上一版模型。收益在超大文档上最明显，但涉及模型 diff 与脏页判定，需单独设计与回归测试。

## 八、复盘：本次开发过程中的三个教训

这三个教训比优化本身更值得留存——它们都是**"单元测试全绿但真机出错"**的典型形态。

### 8.1 等价性测试若喂同一份数据，测不出数据源新鲜度问题

P1 阶段我写了"快速路径与既有路径产出等价"的测试，但**两条路径喂的是同一份夹具数据**，因此它能证明"结构装配逻辑等价"，却完全无法证明"数据源是否实时"。结果：内容取自异步索引导致预览慢一步，测试毫无察觉。

**改进**：对"数据来源"类改动，测试必须包含"数据源本身异常/滞后"的用例（现已有：叶子滞后、容器滞后、索引缺行、索引残留行）。

### 8.2 自造夹具的字段值会掩盖语义错误

我把 `sort` 当成位置排序列，而我的夹具里 `sort` 恰好是递增的"位置感"数值——**真实内核里它是 5/10/20 的类型权重**。夹具越"顺手"，越掩盖错误。

**改进**：夹具必须**照抄内核语义**构造（现已有：`sort` 用 5/10/20、`created` 用同秒值来复现真实不可判定顺序）。

### 8.3 改写既有映射时丢字段，靠仓库里的真实场景测试兜住

重写遗留回退路径时我漏掉了 `children: r.children`，导致 6 个真实列表/超级块集成测试版式退化为 `cover`。这些测试是仓库里既有的、覆盖真实形态的用例——**它们比我新写的用例更有价值**。

**改进**：触及编译链路时，优先运行 `tests/list-superblock-columns.test.ts` 等真实形态集成测试，而非只看自己新增的用例。
