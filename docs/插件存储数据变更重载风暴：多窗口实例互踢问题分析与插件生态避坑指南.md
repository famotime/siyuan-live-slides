## 一、问题现象（实证案例）

| # | 现象 | 观测方式 |
|---|---|---|
| 1 | DevTools Elements 面板中 `<style id="pluginsStylesiyuan-terminal">` 节点**持续消失又出现**（"跳跃"） | 用户在双窗口场景下肉眼捕获并截图 |
| 2 | 插件的 Dock 图标、顶栏按钮、终端页签随之反复销毁重建 | 同上 |
| 3 | PTY 后端进程被反复停止再拉起，端口漂移 | 内核日志与端口观测 |
| 4 | 单窗口使用时一切正常，**开第二个思源窗口后爆发** | 最关键的复现条件 |

本质：**插件在被持续地整体卸载→重载**，样式节点在 `destroyPlugin` 中移除、重新装载时插回，形成肉眼可见的闪烁。

## 二、机制拆解：一次数据变更如何升级为整插件重载（内核契约速查表）

> 引用位置均为 `siyuan-note` 源码。凡涉及插件生命周期与存储的设计，**必须先在此表核对，不得凭直觉推断**。

| # | 契约点 | 结论 | 源码位置 |
|---|---|---|---|
| 1 | **数据变更默认升级为整插件重载** | 生命周期协调器规定：**未覆写 `onDataChanged` 的插件**（即 `plugin.onDataChanged === Plugin.prototype.onDataChanged`），收到数据变更任务时**原位升级为 reload**——完整执行 onunload → destroy → onload → mount | `app/src/plugin/lifecycle.ts` 的 `runDataChange()`；判定函数 `shouldReloadOnDataChange` 见 `app/src/plugin/loader.ts:106` |
| 2 | **插件存储的每次写/删都触发跨实例通知** | `putFile`（非目录）与 `removeFile` 一旦落在 `/data/storage/petal/<插件名>/` 下，内核即广播 `reloadPlugin` 事件并携带 `dataChangePlugins: ["<插件名>"]`；**无内容比对，写入相同内容也触发** | `kernel/api/file.go:909`（putFile）、`:772`（removeFile）；广播实现 `kernel/model/push_reload.go` 的 `PushPluginStorageDataChanged()` |
| 3 | **通知只排除写入方自己** | `Plugin.saveData/removeData` 请求携带 `app`（appId），内核仅排除该 appId，**广播发给其余所有前端实例**（其它桌面窗口、移动端、浏览器访问端） | `app/src/plugin/index.ts` 的 `saveData/removeData`（`app: Constants.SIYUAN_APPID`）；`kernel/model/push_reload.go:113-117` 的 `BroadcastByTypeAndExcludeApp` |
| 4 | **每个思源窗口都是独立插件实例** | 新窗口（页签「移动到新窗口」/ 拖出窗口创建）会**完整加载全部插件**，各自持有独立生命周期；移动端与浏览器访问端同理 | `app/src/window/index.ts:246` 的 `loadPlugins()` |
| 5 | **重载销毁全部插件 UI 与样式** | `destroyPlugin` 移除样式节点、Dock、顶栏按钮、页签、命令注册；重载即全部重建——这就是 DevTools 里看到的节点"跳跃" | `app/src/plugin/uninstall.ts`（`pluginsStyle` 移除）；插入见 `app/src/plugin/loader.ts` 的 `insertPluginCSS()` |
| 6 | **云同步也会触发数据变更** | 同步合并触碰插件存储时以 `reason: "sync"` 广播数据变更——未覆写 `onDataChanged` 的插件**每个同步周期都会被整体重载一次** | `kernel/model/push_reload.go:65-67` 的 `DataChangeReasonSync` |
| 7 | **设置窗口按白名单加载** | 设置窗口只加载声明 `settingsWindow: true` 的插件，常规插件不受设置窗口影响 | `app/src/plugin/loader.ts:127-137` 的 `fetchPluginData()` |

### 2.1 一句话归纳

**「未覆写 `onDataChanged`」把每次跨实例存储写入变成一次整插件重载；「生命周期钩子里写存储」让每次重载必然再产生新的写入；「多前端实例」让写入必然传播给其它实例**——三者叠加即是无限重载风暴。

## 三、风暴形成条件与触发矩阵（共性分析）

| 触发组合 | 后果 | 严重度 |
|---|---|---|
| 未覆写 `onDataChanged` + 生命周期钩子写存储 + **双桌面窗口** | **无限重载风暴**（A 写 → B 重载 → B 卸载再写 → A 重载 → …），UI 持续闪烁、进程反复重启 | 🔴 严重 |
| 未覆写 + 生命周期写存储 + 桌面单窗口，但存在**移动端/浏览器端**在线 | 移动端实例每次都被整插件重载（功能闪断），桌面端无感 | 🟠 中度 |
| 未覆写 + 周期性写存储（定时器持久化状态）+ 任意第二实例 | 第二实例以写入频率持续重载 | 🔴 严重 |
| 未覆写 + **云同步** + 存储随同步变化 | 每个同步周期全体实例重载一次 | 🟠 中度 |
| 已覆写 `onDataChanged`，但覆写实现里**无条件写存储** | 升级被抑制，但形成「热应用乒乓」（双方互写互触发），写入频率取决于覆写逻辑 | 🟡 轻度（需收敛） |
| 已覆写 + 仅在用户显式操作时写存储 | 数据变更只触发对方轻量热应用，**免疫** | 🟢 正常 |

**为什么这是生态共性问题**：契约 1（未覆写即重载）是思源插件的**默认状态**——插件模板不生成 `onDataChanged` 覆写；而「在 `onLayoutReady` 里初始化/发布状态、在 `onunload` 里清理状态」又是插件最自然的写法。单窗口时代这两个习惯毫无问题，**多窗口/多端/同步开启后自动变成陷阱**。一个工作空间装几十个插件时，任何一个命中组合都会拖累全局观感。

## 四、实证案例复盘：siyuan-terminal 双窗口风暴链

以 `siyuan-terminal` v0.9.0 修复前代码为样本，风暴环如下：

```
窗口A onLayoutReady
  └─ 启动 PTY 后端 → publishPtyBackendState()
       └─ saveData("ai-terminal-pty-backend.json")      ← 写入①（排除窗口A自己）
            └─ 内核广播 dataChangePlugins:["siyuan-terminal"]
                 └─ 窗口B 收到 → 未覆写 onDataChanged → 整插件重载
                      ├─ onunload: clearPublishedPtyBackendState()  ← 写入②（removeData，排除B）
                      └─ 重载完成 onLayoutReady: 再启动后端再 publish ← 写入③
                           └─ 内核广播 → 窗口A 收到 → 重载 → 写入②'③' → 窗口B …
                                （无限循环，每一圈销毁重建全部插件 UI）
```

修复后（`cff7fe2`）：写入①③仍在（发布态本身是跨实例会合点），但**重载升级被覆写抑制**、**写入②被移除**，写入只剩单向传播且接收方为轻量热应用——风暴熄灭。详见第五节模式 1/2。

## 五、修复模式（按防御层级）

### 模式 1：覆写 `onDataChanged`，把数据变更降级为热应用（基线，必做）

```ts
async onDataChanged(reason?: "sync" | "overwrite") {
  // 覆写即破坏 plugin.onDataChanged === Plugin.prototype.onDataChanged 判定，
  // 宿主不再升级为整插件重载；此处只做轻量热应用
  this.settings = await loadSettings(this)
  this.applySettings()
}
```

两条纪律：
- **覆写实现必须无写入**（或写入收敛）：若热应用里无条件 `saveData`，会形成热应用乒乓；
- 只重读必要状态、刷新已挂载视图，不做重活。

### 模式 2：生命周期钩子零写入

`onload` / `onLayoutReady` / `onunload` 中的 `saveData/removeData` 是风暴燃料。原则：
- 存储写入只发生在**用户显式动作**（点保存、改设置）或**确实必要时**；
- `onunload` 里的"清理发布态/状态文件"是典型反模式——卸载可能来自对方写入引发的重载，清理写入会"回敬"对方一发触发弹。清理动作移到 `uninstall()`（真正卸载）；**陈旧状态交给新鲜度时间戳 + 读取方过期判断**，而不是靠删除。

### 模式 3：跨实例资源单所有权（发布—探活—复用）

多个实例需要共享一个本机资源（后台进程、服务端口）时，避免各自拉起、互相抢占发布位。模式：

```
启动前：读发布态 → 校验新鲜度（updatedAt 在窗口期内）
        → 探活（本机回环探测资源是否可达）
        → 存活则复用（不写任何存储）；失联才自启并发布
取用时：对复用中的资源复核存活，失联自动收回自持（自愈）
显式重启：跳过复用、收回所有权
```

（siyuan-terminal 的 PTY 后端复用即此模式，探活函数以依赖注入便于测试。）

### 模式 4：写入节流与等值短路

- 高频持久化（定时器、事件驱动）先 `debounce/合并`；
- 写前比对内存值，**等值不写**——注意契约 2：内核**不做内容比对**，相同内容的 putFile 同样触发全端通知，等值短路必须由插件自己做。

## 六、插件自检清单（三分钟）

```bash
# 1. 是否覆写了 onDataChanged？（没有 = 每次跨实例写入都会整插件重载）
grep -rn "onDataChanged" src/

# 2. 写入点分布在哪里？
grep -rn "saveData\|removeData" src/

# 3. 写入是否发生在生命周期钩子内？（onload / onLayoutReady / onunload）
#    —— 逐个检查上一步的命中点
# 4. onunload 是否在删文件/清状态？—— 移到 uninstall()
# 5. 覆写后的 onDataChanged 是否自身有写入？—— 必须无写入或收敛
```

任一第 3/4 项命中 + 未覆写（第 1 项为空）→ 双窗口/多端/同步场景下必然出问题。

## 七、观测与诊断方法

| 手段 | 操作 | 判据 |
|---|---|---|
| DevTools Elements | 观察任一插件的 `<style id="pluginsStyle<名字>">` 节点 | 持续消失又出现 = 该插件在重载风暴中 |
| 内核日志 | 搜索 `reload plugins` | `dataChanges=[...]` 高频重复出现即风暴（`push_reload.go:101` 的 LogInfof） |
| 控制台 | 观察 `plugin <名字> run error` / 反复出现的插件启动日志 | 同一插件的 loaded 日志反复打印 |
| 断点捕获 | Elements → `#message` 容器 → Break on subtree modifications（用于抓 toast 类问题） | 暂停在弹出方调用栈，直接定位来源插件 |

## 八、本插件（siyuan-live-slides）的免疫现状

对照速查表自检：`siyuan-live-slides` **已覆写 `onDataChanged`**（`src/index.ts`：重载全局配置 + 轻量重编译登记，无写入），存储写入仅发生在用户显式修改设置时（`saveGlobalSettings`）——属于触发矩阵的 🟢 行，免疫重载风暴。本插件在同一会话中排查的「演讲者视图占位符」问题与本机制无关（根因是 presenter.html 内联脚本语法错误，另有复盘）。

## 九、生态层面建议

1. **插件模板**：官方模板可为生成的插件类默认带上空的 `onDataChanged` 覆写与注释说明，把"覆写即免疫"变成默认态；
2. **内核侧可选优化**：`putFile` 对插件存储目录做内容哈希比对，等值写入不广播（可显著降低无意义风暴燃料）；
3. **文档**：`onDataChanged` 的"未覆写即重载"语义应在插件 API 文档中显式标注为强契约（当前仅能从 lifecycle 源码读出）；
4. **多窗口测试**：任何插件发版前建议加一条最小回归——开两个思源窗口挂机 30 秒，观察内核日志无重复 `reload plugins` 行。
